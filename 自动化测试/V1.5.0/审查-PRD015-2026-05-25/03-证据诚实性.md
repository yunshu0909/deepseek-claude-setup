# PRD-015 V1.5.0 Provider Certification 证据诚实性审查

## 1. 审查结论

**结论：不可声称“所有测试用例都通过了”，也不可声称 “DeepSeek V1.5.0 provider certification 通过”或 release-ready。**

本结论并不否认已有真实成果：Mac 最新真 Key 开发树报告在其纳入的 55 条 Darwin 用例中均记录为 PASS；Linux 指定报告也记录了 56 条 PASS，包含 TC-044 Hermes 真链路。但依照 PRD 和测试用例规定的发布口径，现有证据存在硬阻断：

1. 缺少 Windows 真实平台报告。
2. Mac 报告为 dirty worktree，且由现代码 release gate 实算会失败。
3. Linux 报告虽顶层写 `passed=true`，却有 8 个 P0 PASS 用例没有 evidence 引用；在 Linux 本机用现代码实算 release gate 会失败。
4. Mac 与 Linux 报告 commit 不一致，不能拼成同一发布候选版本的三平台证据。
5. 现实现的 long task 轮数门禁与测试用例写定的 `[3,20]` 口径不一致。

因此当前可诚实表述为：**Darwin dirty 开发树完成了一轮 55/55 的真 Key 用例执行；Linux 有一份自报 56/56 的 clean 报告但证据引用不满足其自身 release gate；Windows 尚无报告；整体认证未通过。**

## 3. 权威判定口径

PRD 与测试用例对“通过”的门槛是一致且严格的：

| 口径 | 文档依据 | 对当前陈述的含义 |
|---|---|---|
| Mac、Windows、Linux 必须真实分别执行 | PRD `:203-226`；测试用例 `:21-22` | 单个平台 PASS 不能推出认证通过 |
| 所有 P0 必须 PASS，且每平台有完整 true-key 矩阵 | PRD `:277-282`；测试用例 `:21` | 缺 Windows 或缺 evidence 即不能通过 |
| dirty 正式报告不得进入 release gate PASS | PRD `:182`、`:242`；测试用例 TC-050 | Mac dirty 报告只能作开发调试证据 |
| `BLOCKED` / `SKIPPED` 不等于 PASS | 测试用例 `:20-21` | 缺平台、缺 Key、未执行不能被口头抹平 |
| Linux 必须包含 systemd + Hermes 真链路 | PRD `:217`、`:244`、`:280`；TC-044 | Linux 需要可读的 TC-044 证据 |
| 长任务必须在 3 至 20 轮内且含黑盒复测/静态检查 | TC-037 `:634-656`；TC-038 `:669-675`；TC-056 `:956-967` | runner 必须按同一口径形成证据 |

## 4. 阻断发现

### P0-1 缺少 Windows 真实报告

在指定本地报告目录及 `自动化测试/V1.5.0` 中，仅发现 Darwin 顶层认证报告；未发现 `deepseek-win32-*` 或 Windows 报告。Linux 报告仅由用户给定的服务器路径取得。

这直接违反三平台独立执行与 release gate 前置条件。即便 Mac 和 Linux 各自完全可信，Windows 缺失也足以否定“全过”。

### P0-2 Mac 最新真 Key 报告为 dirty，且不能通过现 release gate

本地最新完整 Darwin 报告：

| 字段 | 值 |
|---|---|
| run | `deepseek-darwin-2026-05-25T11-12-10-094Z` |
| platform | `darwin` |
| branch / commit | `codex/v1.5.0-provider-certification` / `aad165c` |
| report 顶层结论 | `passed=true`，`PASS=55, FAIL=0, BLOCKED=0, SKIPPED=0` |
| isDirty | `true` |
| TC-037 / TC-038 | 均 `PASS`，证据引用在本机可读 |

将该报告交给现代码
`scripts/certification/release-gate.js:56-117` 的 `validatePlatformReport()` 实算，结果为失败，失败项包括：

- `worktree is dirty`
- `platform provenance conflicts with expected platform`

第二项还暴露出现代码口径缺陷：

- `scripts/certification/platform-context.js:70-77` 用 `os.release()` 记录 Mac 的 `osRelease`，实际报告值为 `25.2.0`。
- `scripts/certification/release-gate.js:41-47` 却要求 Darwin 的 `osRelease` 匹配文本 `Darwin`。

因此这份 Mac 报告可支持“dirty 开发树本轮 55 条用例状态为 PASS”，但不能支持正式平台门禁通过。

### P0-3 Linux 顶层 PASS 与 evidence 可读性门禁相矛盾

对用户指定的 Linux 报告进行服务器本机安全解析：

| 字段 | 值 |
|---|---|
| platform | `linux` |
| branch / commit | `codex/v1.5.0-provider-certification` / `d40d393` |
| isDirty | `false` |
| report 顶层结论 | `passed=true`，`PASS=56, FAIL=0, BLOCKED=0, SKIPPED=0` |
| TC-044 | `PASS`，`true-key`，有 1 个 evidence 引用 |

但在 Linux 本机直接用该部署目录中的现 `validatePlatformReport()` 校验，返回 `passed=false`。以下 P0 PASS 项无可读 evidence 引用：

| 无 evidenceRefs 的 P0 PASS 用例 |
|---|
| `TC-014`、`TC-015`、`TC-016`、`TC-017`、`TC-018`、`TC-019`、`TC-038`、`TC-051` |

这不是本地读取不到远端绝对路径造成的假象：校验是在 Linux 报告所在服务器本机执行，且这些条目的 `evidenceRefs` 本身为空数组。

现本地实现展示了与该结果一致的生成口径：

- `scripts/certify-provider.js:210-227` 只从 `clientResult.report?.jsonPath/mdPath` 填入客户端用例 evidence。
- `scripts/certification/report-writer.js:70-104` 在写顶层 `passed` 时只核验 P0 状态与正向断言，不核验证据引用是否存在或可读。
- `scripts/certification/release-gate.js:82-97` 到 release gate 才拒绝 PASS 但无可读证据的 P0。

所以 Linux 报告的 `passed=true` 不是发布可接受的“证据已通过”，而是报告生成时口径宽于 release gate 的假绿风险实例。

### P0-4 跨平台 commit 不一致

| 平台 | commit | clean |
|---|---:|---:|
| Mac 最新完整报告 | `aad165c` | 否 |
| Linux 指定报告 | `d40d393` | 是 |
| Windows | 无报告 | 不适用 |

`release-gate.js:132-149` 会拒绝跨平台 commit 不一致的报告集合。当前即使补上一份 Windows 报告，也不能把上述 Mac 与 Linux 两份现存报告直接汇总为通过。

## 5. 专项核验

### 5.1 Long task 轮数门禁

测试用例 TC-037/TC-038 规定轮数范围为 `[3,20]`。现实现则为：

- `scripts/client-e2e.js:24-25`：`LONG_TASK_MIN_TOOL_ROUNDS=3`，`LONG_TASK_MAX_TOOL_ROUNDS=10`。
- `scripts/client-e2e.js:557-577`、`:636-656`：按日志中的 `MSG_DONE` / `RESPONSES_DONE` 数计 `toolRounds` 并以 `[3,10]` 放行。
- `test/certification.test.js:310-313`：测试固定断言最大轮数为十轮。

这是实现与事实源用例的不一致。最新 Mac 报告中的 `codex-long toolRounds=8`、`claude-long toolRounds=9`，同时具备模型自测、runner 黑盒复测、静态检查及无 gateway 失败标记，因此这两次执行在更严格的十轮约束下本身可成立；但现 runner 不能证明自己完整实现了 PRD 书写的 `[3,20]` 门禁口径，不能用作“所有用例严格按文档通过”的证据。

### 5.2 Mac dirty / 401

- dirty：最新 Darwin 真 Key 报告明确 `isDirty=true`，并列出修改/未跟踪文件；`TEST_REPORT.md` 也明确写着 `PASS on dirty Mac worktree` 且“不得作为正式 release report”。此处记录是诚实的，但其结论只限开发树。
- 401：最新 Darwin 证据中的若干 Codex PASS 结果包含 `https://chatgpt.com/backend-api/plugins/featured` 的 `401 Unauthorized` 插件缓存预热告警。未观察到这些命中来自 DeepSeek gateway 或 `RESPONSES_FAILED`；TC-023 的顶层证据也只声称没有 `RESPONSES_FAILED`。因此该 401 不能据此定性为 DeepSeek 认证失败，但“CLI 运行日志无告警/无 401”亦不能被声称。

### 5.3 中断与未完成运行

- 本地存在目录 `deepseek-darwin-2026-05-25T11-06-15-022Z/`，目录中没有 `report.json` 或 `report.md`。其成因无法仅凭空目录定性，但它明确不是可计入 PASS 的完成运行。
- 最新 Mac 长任务证据未发现 `MSG_FAILED` 或 `RESPONSES_FAILED`；`codex-long` 的 stderr 存在 curated plugin git sync `timed out after 30s` 告警，但任务最终为 PASS，黑盒复测与静态检查均通过。该超时属于旁路插件同步告警，不等同于认证主链路中断。

### 5.4 报告可读性与 `passed` 字段含义

- Mac 最新完整报告的 P0 evidence refs 在本机可读，但 release gate 仍因 dirty/provenance 失败。
- Linux 报告的人机顶层结论为 PASS，却未在生成时暴露 8 个 P0 evidence 缺失为失败；只有重新执行 release gate 才看出矛盾。
- `report-writer.js:83-100` 将 `passed` 定义为所需 P0 的状态通过，不等价于“所有尝试过的运行均通过”，也不等价于“三平台 release gate 通过”。例如 P1 项即便失败也不会单凭该聚合逻辑使 `passed=false`；本次已读的两份完整平台报告虽未出现该现象，字段语义仍不能被扩大解释。

## 7. 允许与禁止的对外表述

**允许表述：**

> 在 2026-05-25 生成的 dirty Mac 开发树报告中，Darwin 适用的 55 条用例记录为 PASS；另有一份 Linux clean 报告自报 56 条 PASS 并含 TC-044，但其 P0 evidence 引用未满足 release gate。Windows 仍无报告，跨平台门禁未通过。

**禁止表述：**

- “所有测试用例都通过了。”
- “DeepSeek V1.5.0 provider certification 已通过。”
- “三平台认证全绿。”
- “已经 release-ready。”

## 8. 最终判定

**FAIL（针对“是否所有测试用例都通过了”这一陈述的证据充分性）。**

最短充分依据是：Windows 报告缺失；Mac 报告 dirty 且现 gate 拒绝；Linux 报告虽自报 PASS，但在服务器本机由现 gate 实算因 8 个 P0 evidence 引用缺失而失败；Mac/Linux 还不在同一 commit。任何一项都足以否定全过，四项同时存在。
