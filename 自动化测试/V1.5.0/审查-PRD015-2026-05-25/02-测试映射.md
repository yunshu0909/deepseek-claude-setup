## 2. P0 阻断问题

### P0-1 `TC-054` / `TC-055` 只验“自报类型 + 文件存在”，可让伪造矩阵通过 release gate

- `scripts/certification/release-gate.js:50-53` 对 `evidenceRefs` 仅检查字符串路径存在，不验证证据内容对应 TC、运行类型或 runner 产物结构；`scripts/certification/release-gate.js:99-110` 仅相信报告自报的 `evidenceType === "true-key"`。
- `test/certification.test.js:29-31,65-78,143-147` 把全部 P0 用例都指向同一个仅含 `{"fixture":true}` 的文件，且将这一报告矩阵断言为可通过。
- 认证器自己的“有效报告”fixture 同样将全部 P0 指向单一占位文件：`scripts/certify-provider.js:494-505,549-570`。
- 后果：复制或构造报告时，只需填入所需 `TC`、将类型声明为 `true-key`、提供任意存在文件，即可绕过 `TC-054/055` 的核心目标；这属于批量假 PASS 通路。
- 关联判定：`TC-054 GAP`、`TC-055 GAP`。

### P0-2 `TC-044` 可 PASS 而没有证明日志确实被扫描、临时纳管确实已清理

- Linux runner 以 trap 声明清理：`scripts/certification/linux-hermes-smoke.js:28-34`，但返回结果只计算进程退出、active、health、marker、diagnostic、model：`scripts/certification/linux-hermes-smoke.js:90-109`，没有在退出后断言临时目录和 transient unit 已消失。
- Key 检查使用 `! grep -F "$DEEPSEEK_API_KEY" "$DEEPSEEK_CLAUDE_LOG_PATH"`：`scripts/certification/linux-hermes-smoke.js:51`。若日志文件不存在，`grep` 的错误状态也会被 `!` 反转为成功，未证明实际日志经过扫描。
- 后果：`TC-044` 的 P0 通过结论缺少“日志无 Key”和“测试后置清理”的正向证据。
- 关联判定：`TC-044 GAP`。

### P0-3 `TC-056` 的二次防作弊校验对缺失 `staticChecks` 为真空通过

- `scripts/certify-provider.js:395-402` 使用 `Object.values(item.staticChecks || {}).every(Boolean)`；当 `staticChecks` 缺失或为空对象时结果为 `true`，未强制三项字段存在。
- 客户端当前确会生成三项静态检查：`scripts/client-e2e.js:730-746`，且长任务判定会读取它们：`scripts/client-e2e.js:553-580,632-659`；问题在于 `TC-056` 作为独立反假绿审查没有验证报告 schema 的必填字段。
- 后果：被裁剪或伪造的长任务明细可绕过 `TC-056` 的独立校验。
- 关联判定：`TC-056 GAP`。

| 类型 | 是否存在 | 结论 |

## 6. 审计门禁建议

在修复并补充针对性自动化之前，不应将当前映射审计结论表述为“56 条可信全绿”或“release gate 可阻断复制/伪造报告”。最低阻断项是：

1. 让 release gate 校验证据结构与每条 TC 的执行产物绑定，而不是只检查文件存在和 `evidenceType` 字面值。
2. 为 provenance 加入不可由报告自填即可伪造的绑定机制，至少拒绝同一占位 evidence 支撑完整三平台 P0 矩阵的 fixture。
3. 对 Linux Hermes 补日志文件存在/扫描成功、退出后 transient unit 与临时目录清理的可审计断言。
4. 对齐长任务轮次口径与 `TC-056` 必填字段校验；扩展 `TC-047` 到所有临时资源来源。
